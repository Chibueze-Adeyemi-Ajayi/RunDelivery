ANSWERS TO ASSESSMENT QUESTIONS

When over 1000 drivers send location updates every few seconds, the following challenges can arise:

  • Server Overload: High frequency of incoming requests can exhaust CPU and memory resources.
  • Database Bottlenecks: Synchronous database writes for every update can create a massive queue and slow down the entire system.
  • Massive Data Growth: Storing every single historical coordinate point can lead to rapid storage depletion.
  • Increased Latency: Network congestion and processing delays can result in stale location data being shown to customers.

To scale a real-time system to handle significant growth, I would implement the following strategies:

  • Event-Driven Architecture: Use a robust message queue system (like RabbitMQ or Kafka) to decouple data ingestion from processing.
  • Horizontal Scaling: Utilize containerization (Docker/Kubernetes/Swarm) to spin up multiple instances of the API and WebSocket servers behind a load balancer.
  • WebSocket Optimization: Use a distributed WebSocket strategy (using Redis Adapter) to sync messages across multiple server nodes.
  • Geospatial Indexing: Implement specialized database indexing (like MongoDB's 2dsphere) to optimize "nearby" queries.

Choosing between Redis and a dedicated Message Broker depends on the specific requirements:

  • Redis: Best for quick I/O operations, caching latest state (e.g., current driver location), and simple Pub/Sub needs. It is extremely fast due to being in-memory.
  • Message Broker: Excels at reliable inter-process communication, complex routing, ensuring message delivery (persistence), and handling tasks that need to be processed asynchronously by different services.

When a client is offline, the following occurs:

  • Missed Event: In a standard WebSocket implementation without persistence, the client misses the event entirely. The server attempts to push the data, but since the connection is broken, the packet is discarded.
  • Lack of Buffering: By default, Socket.IO does not buffer events for offline clients unless specifically configured with an acknowledgement system or a persistent message store.

To ensure data consistency after a reconnection, the following patterns are used:

  • State Synchronization: Upon re-establishing the connection (the `connect` event), the client should immediately trigger a REST API call or a pull-based socket event (e.g., `get_order_status`) to fetch the current, authoritative state from the database.
  • Event Repositories: Implementing an event store (like a message queue with persistence) allows the client to "catch up" by requesting all events that occurred after its last recorded timestamp.
  • Latest State Caching: Using Redis to store the "Latest Known Location" allows the server to push the most recent data to the client as soon as they rejoin the room.
